## PostgreSQL Basics

### Q1. What is PostgreSQL?
**Answer:** PostgreSQL (often called "Postgres") is a powerful, open-source object-relational database management system (ORDBMS). It emphasizes extensibility and SQL standards compliance. It supports advanced data types, full-text search, JSON, geospatial data (via PostGIS), and custom extensions. It has been actively developed for over 35 years.

---

### Q2. What are the key features of PostgreSQL?
**Answer:** Key features include:
- ACID-compliant transactions
- MVCC (Multi-Version Concurrency Control)
- Rich data types (arrays, JSON, hstore, ranges, UUID, etc.)
- Full-text search
- Extensibility (custom types, functions, operators)
- Table inheritance and partitioning
- Foreign data wrappers (FDW)
- Logical and physical replication
- Row-level security (RLS)
- Advanced indexing (B-tree, Hash, GIN, GiST, BRIN, SP-GiST)

---

### Q3. What is the difference between PostgreSQL and MySQL?
**Answer:**
- **Standards compliance**: PostgreSQL is more strictly SQL-compliant.
- **Data types**: PostgreSQL offers richer native types (arrays, JSON, ranges, custom types).
- **MVCC**: Both support it, but PostgreSQL's implementation uses tuple versioning vs. MySQL's undo log.
- **Extensibility**: PostgreSQL allows custom functions, operators, and types.
- **Replication**: PostgreSQL has built-in logical replication; MySQL has binary log replication.
- **Licensing**: PostgreSQL uses the PostgreSQL License (permissive); MySQL is GPL with Oracle's commercial license.
- **Performance**: MySQL is often faster for simple read-heavy workloads; PostgreSQL excels in complex queries and write-heavy workloads.

---

### Q4. What does ACID stand for?
**Answer:**
- **Atomicity** – A transaction is all-or-nothing; if any part fails, the whole transaction is rolled back.
- **Consistency** – A transaction brings the database from one valid state to another, enforcing all rules and constraints.
- **Isolation** – Concurrent transactions execute as if they were sequential; intermediate states are not visible to others.
- **Durability** – Once a transaction is committed, it remains committed even in the event of a system failure.

---

### Q5. What is MVCC in PostgreSQL?
**Answer:** Multi-Version Concurrency Control (MVCC) is PostgreSQL's concurrency mechanism. Instead of locking rows for reads, PostgreSQL maintains multiple versions of each row (tuples). Readers see a consistent snapshot of data as of the start of their transaction, and writers create new row versions without blocking readers. Dead tuple versions are later cleaned up by the VACUUM process.

---

### Q6. What is a schema in PostgreSQL?
**Answer:** A schema is a named namespace within a database that contains tables, views, indexes, sequences, functions, and other objects. The default schema is `public`. Schemas help organize objects and control access. A database can have multiple schemas.

```sql
CREATE SCHEMA accounting;
CREATE TABLE accounting.invoices (id SERIAL PRIMARY KEY, amount NUMERIC);
```

---

### Q7. What is the `search_path` in PostgreSQL?
**Answer:** `search_path` is a session-level or role-level setting that specifies the order in which schemas are searched when an unqualified object name is used. The default is `"$user", public`.

```sql
SET search_path TO accounting, public;
```

---

### Q8. What is a sequence in PostgreSQL?
**Answer:** A sequence is a database object that generates unique integer values, typically used for auto-incrementing primary keys. `SERIAL` and `BIGSERIAL` types create sequences automatically.

```sql
CREATE SEQUENCE order_seq START 1 INCREMENT 1;
SELECT nextval('order_seq'); -- 1
SELECT nextval('order_seq'); -- 2
```

---

### Q9. What is the difference between `SERIAL`, `BIGSERIAL`, and `IDENTITY`?
**Answer:**
- `SERIAL` / `BIGSERIAL` — legacy shorthand that creates a sequence and sets a `DEFAULT nextval(...)`. Not true SQL standard.
- `GENERATED ALWAYS AS IDENTITY` / `GENERATED BY DEFAULT AS IDENTITY` — SQL standard (PostgreSQL 10+), more robust, prevents accidental manual inserts (`ALWAYS`) or allows them (`BY DEFAULT`).

```sql
-- Modern preferred approach:
CREATE TABLE users (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

---

### Q10. What is the `pg_catalog` schema?
**Answer:** `pg_catalog` is a system schema that contains all system tables (like `pg_tables`, `pg_indexes`, `pg_roles`) and built-in functions. It is always included in the `search_path` automatically. You can query it to inspect database metadata.

---

### Q11. What is `information_schema`?
**Answer:** `information_schema` is a standard SQL schema that provides views for querying database metadata (tables, columns, constraints, etc.) in a portable, SQL-standard way. Unlike `pg_catalog`, it works across different database systems.

```sql
SELECT table_name FROM information_schema.tables WHERE table_schema = 'public';
```

---

### Q12. What is the difference between a database and a schema in PostgreSQL?
**Answer:** A **database** is a separate environment with its own storage, connections, and settings. Cross-database queries require Foreign Data Wrappers. A **schema** is a namespace within a database — all schemas in the same database share the same connection and can query each other without extra configuration.

---

### Q13. How do you connect to PostgreSQL from the command line?
**Answer:** Use the `psql` client:

```bash
psql -h localhost -p 5432 -U postgres -d mydb
# or with a connection string:
psql "postgresql://postgres:password@localhost:5432/mydb"
```

---

### Q14. What are tablespaces in PostgreSQL?
**Answer:** Tablespaces allow database administrators to define locations on the file system where database objects are stored. This lets you distribute data across multiple disks or use faster storage for critical tables.

```sql
CREATE TABLESPACE fast_disk LOCATION '/mnt/ssd/pgdata';
CREATE TABLE hot_data (...) TABLESPACE fast_disk;
```

---

### Q15. What is the `pg_hba.conf` file?
**Answer:** `pg_hba.conf` (Host-Based Authentication) is a configuration file that controls client authentication. It defines which users can connect to which databases from which hosts using which authentication methods (e.g., `trust`, `password`, `md5`, `scram-sha-256`, `peer`, `cert`).

---

### Q16. What is the `postgresql.conf` file?
**Answer:** `postgresql.conf` is the main server configuration file. It controls memory settings (`shared_buffers`, `work_mem`), connection limits (`max_connections`), WAL settings, logging, autovacuum, and many other server parameters.

---

### Q17. What is WAL in PostgreSQL?
**Answer:** WAL (Write-Ahead Log) is a logging mechanism where all changes are first written to the WAL log before being applied to data files. This ensures durability (changes can be replayed after a crash) and is the foundation for replication and Point-In-Time Recovery (PITR).

---

### Q18. What is `pg_dump` and `pg_restore`?
**Answer:**
- `pg_dump` exports a database to a file (SQL script, custom, directory, or tar format).
- `pg_restore` restores from a non-SQL format dump.

```bash
pg_dump -Fc mydb > mydb.dump          # Custom format backup
pg_restore -d newdb mydb.dump          # Restore
pg_dump mydb > mydb.sql               # Plain SQL backup
psql newdb < mydb.sql                  # Restore plain SQL
```

---

### Q19. What is `VACUUM` in PostgreSQL?
**Answer:** `VACUUM` reclaims storage occupied by dead tuples (obsolete row versions created by updates and deletes). Due to MVCC, old versions aren't immediately deleted. `VACUUM ANALYZE` also updates planner statistics. `VACUUM FULL` rewrites the entire table but holds an exclusive lock. `autovacuum` runs `VACUUM` automatically in the background.

---

### Q20. What is `ANALYZE` in PostgreSQL?
**Answer:** `ANALYZE` collects statistics about table contents (column value distributions, row count estimates) and stores them in `pg_statistic`. The query planner uses these statistics to choose optimal execution plans. Running `VACUUM ANALYZE` after bulk loads is a best practice.

---

### Q21. What is `EXPLAIN` and `EXPLAIN ANALYZE`?
**Answer:**
- `EXPLAIN` shows the query planner's execution plan without running the query.
- `EXPLAIN ANALYZE` actually executes the query and shows both the planned and actual execution details (time, rows).

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
```

---

### Q22. What is the PostgreSQL process architecture?
**Answer:** PostgreSQL uses a multi-process architecture:
- **postmaster** – The main process that accepts connections
- **backend processes** – One per client connection, handles queries
- **background processes** – autovacuum, WAL writer, checkpointer, background writer, stats collector, etc.
Unlike many databases, PostgreSQL does not use threads; each connection spawns a separate OS process, which is why connection poolers (PgBouncer) are important at scale.

---

### Q23. What is PgBouncer?
**Answer:** PgBouncer is a lightweight connection pooler for PostgreSQL. Since each PostgreSQL connection is a separate process, many idle connections waste memory. PgBouncer maintains a pool of backend connections and multiplexes client connections, reducing overhead significantly.

---

### Q24. What is logical replication in PostgreSQL?
**Answer:** Logical replication replicates data changes at the logical (row) level rather than the physical (byte) level. It uses the publish/subscribe model and supports selective replication of specific tables, replication between different PostgreSQL major versions, and replication to non-PostgreSQL systems.

---

### Q25. What is streaming replication?
**Answer:** Streaming replication is PostgreSQL's built-in physical replication mechanism. The primary server streams WAL records to standby servers in real time. Standbys can be hot standby (readable) or warm standby (not readable). It replicates the entire cluster, not individual tables.

---

### Q26. What is the difference between synchronous and asynchronous replication?
**Answer:**
- **Asynchronous** (default): The primary commits without waiting for standbys to confirm receipt. Faster but risks small data loss if primary fails.
- **Synchronous**: The primary waits for at least one standby to confirm the WAL is written before committing. Zero data loss but higher latency.

---

### Q27. What is Point-In-Time Recovery (PITR)?
**Answer:** PITR allows restoring a PostgreSQL database to any point in the past by replaying WAL records from a base backup. Useful for recovering from accidental data deletion or corruption.

---

### Q28. What is an extension in PostgreSQL?
**Answer:** An extension is a packaged set of database objects (functions, types, operators, indexes) that can be installed into a database. Popular extensions include `postgis`, `pg_trgm`, `uuid-ossp`, `hstore`, `pg_stat_statements`, `pgcrypto`, and `citext`.

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
SELECT uuid_generate_v4();
```

---

### Q29. What is `pg_stat_statements`?
**Answer:** `pg_stat_statements` is an extension that tracks execution statistics (calls, total/mean execution time, rows) for all SQL statements. Essential for identifying slow or frequently executed queries.

```sql
SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;
```

---

### Q30. What is the role of `shared_buffers` in PostgreSQL?
**Answer:** `shared_buffers` is the amount of memory allocated for PostgreSQL's shared buffer cache — the in-memory cache for data pages. A common recommendation is to set it to 25% of system RAM. Increasing it reduces disk I/O for frequently accessed data.

---

## Data Types

### Q31. What are the main numeric types in PostgreSQL?
**Answer:**
- `SMALLINT` (2 bytes, -32768 to 32767)
- `INTEGER` / `INT` (4 bytes, ~±2 billion)
- `BIGINT` (8 bytes, ~±9.2 quintillion)
- `NUMERIC(precision, scale)` / `DECIMAL` — exact, arbitrary precision, ideal for money
- `REAL` (4 bytes, floating point, inexact)
- `DOUBLE PRECISION` (8 bytes, floating point, inexact)

---

### Q32. What is the difference between `NUMERIC` and `FLOAT`?
**Answer:** `NUMERIC` (or `DECIMAL`) stores values with exact precision and is suitable for financial calculations. `FLOAT` (`REAL` / `DOUBLE PRECISION`) stores values in IEEE 754 floating-point format, which is inexact due to binary representation. Never use `FLOAT` for money.

---

### Q33. What are character types in PostgreSQL?
**Answer:**
- `CHAR(n)` — fixed-length, padded with spaces. Rarely useful.
- `VARCHAR(n)` — variable-length, max `n` characters.
- `TEXT` — variable-length, unlimited. The preferred type for strings in PostgreSQL, with no performance difference from `VARCHAR`.

---

### Q34. What is the `UUID` type?
**Answer:** `UUID` stores a universally unique identifier (128 bits, displayed as 32 hex characters in groups). Ideal for distributed systems where auto-increment IDs would collide. Generate with `uuid_generate_v4()` (from `uuid-ossp`) or the built-in `gen_random_uuid()` (PostgreSQL 13+).

---

### Q35. What are array types in PostgreSQL?
**Answer:** PostgreSQL natively supports arrays of any type. You can store, query, and index arrays.

```sql
CREATE TABLE products (id SERIAL, tags TEXT[]);
INSERT INTO products (tags) VALUES ('{electronics, sale}');
SELECT * FROM products WHERE 'sale' = ANY(tags);
```

---

### Q36. What is the `JSONB` type and how does it differ from `JSON`?
**Answer:**
- `JSON` stores the raw JSON text, preserving whitespace and key order. Parsing happens on every read.
- `JSONB` stores JSON in a decomposed binary format. It's faster to query and supports indexing (GIN indexes). Key order is not preserved, and duplicate keys are deduplicated.
**Use `JSONB` for almost all cases.**

---

### Q37. How do you query `JSONB` data?
**Answer:** Use the `->` (returns JSON) and `->>` (returns text) operators, and `@>` (contains), `?` (key exists), `#>` (path navigation).

```sql
SELECT data->>'name' FROM users WHERE data @> '{"role": "admin"}';
SELECT data#>>'{address, city}' FROM users;
```

---

### Q38. What is the `HSTORE` type?
**Answer:** `hstore` is a key-value store extension that stores sets of key-value pairs in a single column. It predates `JSONB` and is simpler for flat key-value data but lacks JSON's nested structure support. `JSONB` is generally preferred today.

---

### Q39. What are range types in PostgreSQL?
**Answer:** Range types represent a range of values with a lower and upper bound. Built-in range types include `int4range`, `int8range`, `numrange`, `tsrange`, `tstzrange`, `daterange`. They support containment, overlap, and adjacency operators.

```sql
SELECT '[2024-01-01, 2024-12-31]'::daterange @> '2024-06-15'::date; -- true
```

---

### Q40. What is the `BYTEA` type?
**Answer:** `BYTEA` stores raw binary data (byte arrays). Useful for storing files, encrypted data, or binary blobs directly in the database. Input/output is in hex escape format by default.

---

### Q41. What is the `BOOLEAN` type?
**Answer:** `BOOLEAN` stores true/false values. Accepts `TRUE`/`FALSE`, `'t'`/`'f'`, `'yes'`/`'no'`, `'on'`/`'off'`, `1`/`0`.

---

### Q42. What date and time types does PostgreSQL support?
**Answer:**
- `DATE` – calendar date (year, month, day)
- `TIME [WITHOUT TIME ZONE]` – time of day
- `TIMETZ` / `TIME WITH TIME ZONE` – time of day with timezone
- `TIMESTAMP [WITHOUT TIME ZONE]` – date and time
- `TIMESTAMPTZ` / `TIMESTAMP WITH TIME ZONE` – stored as UTC, displayed in session timezone. **Prefer `TIMESTAMPTZ`.**
- `INTERVAL` – duration (e.g., `'3 hours 30 minutes'`)

---

### Q43. What is the `ENUM` type?
**Answer:** An `ENUM` is a static, ordered set of string values. It enforces that a column only accepts predefined values.

```sql
CREATE TYPE mood AS ENUM ('happy', 'neutral', 'sad');
CREATE TABLE person (name TEXT, current_mood mood);
```

Adding new values is possible (`ALTER TYPE mood ADD VALUE 'excited'`) but removing values is complex.

---

### Q44. What is the `CITEXT` type?
**Answer:** `CITEXT` (case-insensitive text) is an extension type that behaves like `TEXT` but comparisons are case-insensitive without needing `LOWER()` calls. Useful for email addresses or usernames.

```sql
CREATE EXTENSION citext;
CREATE TABLE users (email CITEXT UNIQUE);
```

---

### Q45. What is the `MONEY` type and should you use it?
**Answer:** The `MONEY` type stores currency amounts with a fixed fractional precision based on locale. It is generally **not recommended** because it's locale-dependent and has poor interoperability. Use `NUMERIC(19, 4)` instead for financial data.

---

### Q46. What is the `TSVECTOR` type?
**Answer:** `TSVECTOR` is a sorted list of lexemes (normalized words with positional information) used for full-text search. It's the pre-processed form of text that PostgreSQL's FTS engine searches against.

```sql
SELECT to_tsvector('english', 'The quick brown fox');
-- 'brown':3 'fox':4 'quick':2
```

---

### Q47. What is `TSQUERY`?
**Answer:** `TSQUERY` represents a full-text search query — a set of lexemes connected by boolean operators (`&`, `|`, `!`). The `@@` operator matches a `TSVECTOR` against a `TSQUERY`.

```sql
SELECT * FROM articles WHERE to_tsvector('english', body) @@ to_tsquery('quick & fox');
```

---

### Q48. What are geometric types in PostgreSQL?
**Answer:** PostgreSQL supports geometric types: `POINT`, `LINE`, `LSEG`, `BOX`, `PATH`, `POLYGON`, `CIRCLE`. They support geometric operations and can be indexed with GiST indexes. For serious geospatial work, the PostGIS extension is preferred.

---

### Q49. What is the `INET` and `CIDR` type?
**Answer:**
- `INET` stores an IPv4 or IPv6 host address with an optional subnet mask.
- `CIDR` stores network addresses (the host part must be zero).
Both support operators for subnet comparisons and are more efficient than storing IPs as strings.

---

### Q50. What is the `XML` type?
**Answer:** The `XML` type stores XML data and validates it at insert time. PostgreSQL provides XPath functions to query XML. However, `JSONB` has largely superseded `XML` for semi-structured data in modern applications.

---

## Queries & SQL

### Q51. What is the difference between `WHERE` and `HAVING`?
**Answer:**
- `WHERE` filters rows **before** aggregation (operates on individual rows).
- `HAVING` filters groups **after** `GROUP BY` aggregation (operates on aggregated results).

```sql
SELECT department, COUNT(*) FROM employees
WHERE salary > 50000         -- filter rows first
GROUP BY department
HAVING COUNT(*) > 5;         -- filter groups after
```

---

### Q52. What are the types of JOINs in PostgreSQL?
**Answer:**
- `INNER JOIN` – rows matching in both tables
- `LEFT JOIN` – all rows from left, matching from right (NULL if no match)
- `RIGHT JOIN` – all rows from right, matching from left
- `FULL OUTER JOIN` – all rows from both, NULL where no match
- `CROSS JOIN` – Cartesian product of both tables
- `SELF JOIN` – joining a table to itself

---

### Q53. What is a CTE (Common Table Expression)?
**Answer:** A CTE (`WITH` clause) defines a temporary named result set that can be referenced in the main query. CTEs improve readability, allow recursion, and can be referenced multiple times.

```sql
WITH high_earners AS (
  SELECT * FROM employees WHERE salary > 100000
)
SELECT department, COUNT(*) FROM high_earners GROUP BY department;
```

---

### Q54. What is a recursive CTE?
**Answer:** A recursive CTE references itself to traverse hierarchical or graph data (like org charts, trees, or bill of materials).

```sql
WITH RECURSIVE org_chart AS (
  SELECT id, name, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, oc.level + 1
  FROM employees e JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart ORDER BY level;
```

---

### Q55. What are window functions?
**Answer:** Window functions perform calculations across a set of rows related to the current row, without collapsing them into a single aggregate. They use the `OVER` clause.

```sql
SELECT name, salary,
  RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rank,
  AVG(salary) OVER (PARTITION BY department) AS dept_avg
FROM employees;
```

---

### Q56. What window functions are available in PostgreSQL?
**Answer:** Common window functions include:
- **Ranking**: `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `NTILE(n)`, `PERCENT_RANK()`, `CUME_DIST()`
- **Navigation**: `LAG(col, n)`, `LEAD(col, n)`, `FIRST_VALUE(col)`, `LAST_VALUE(col)`, `NTH_VALUE(col, n)`
- **Aggregate as window**: `SUM()`, `AVG()`, `COUNT()`, `MIN()`, `MAX()` — all can be used with `OVER()`

---

### Q57. What is the difference between `RANK()` and `DENSE_RANK()`?
**Answer:**
- `RANK()` leaves gaps after ties (1, 1, 3, 4...)
- `DENSE_RANK()` does not leave gaps (1, 1, 2, 3...)
- `ROW_NUMBER()` always gives unique sequential numbers regardless of ties

---

### Q58. What is a subquery?
**Answer:** A subquery is a query nested inside another query. It can appear in `SELECT`, `FROM`, `WHERE`, or `HAVING` clauses.

```sql
SELECT * FROM orders
WHERE customer_id IN (SELECT id FROM customers WHERE country = 'India');
```

---

### Q59. What is the difference between `IN` and `EXISTS`?
**Answer:**
- `IN` evaluates the subquery and checks if a value is in the result set. Can be slow with large result sets and doesn't short-circuit.
- `EXISTS` returns `TRUE` as soon as the subquery finds the first matching row (short-circuits). Generally faster for correlated subqueries with large datasets.

---

### Q60. What is a lateral join?
**Answer:** `LATERAL` allows a subquery in the `FROM` clause to reference columns from preceding table expressions — like a correlated subquery but returning multiple rows.

```sql
SELECT u.name, recent.title
FROM users u,
LATERAL (
  SELECT title FROM posts WHERE user_id = u.id ORDER BY created_at DESC LIMIT 3
) recent;
```

---

### Q61. What is the difference between `UNION` and `UNION ALL`?
**Answer:**
- `UNION` combines results and removes duplicates (sorts to deduplicate, slower).
- `UNION ALL` combines results including duplicates (no deduplication, faster).

---

### Q62. What is the `DISTINCT ON` clause?
**Answer:** `DISTINCT ON` is a PostgreSQL extension that returns the first row of each group defined by the specified expressions. Unlike standard `DISTINCT`, it lets you control which row is kept via `ORDER BY`.

```sql
SELECT DISTINCT ON (customer_id)
  customer_id, order_date, total
FROM orders
ORDER BY customer_id, order_date DESC; -- keeps most recent order per customer
```

---

### Q63. What is the `RETURNING` clause?
**Answer:** `RETURNING` allows `INSERT`, `UPDATE`, and `DELETE` statements to return column values of the affected rows, avoiding an extra `SELECT`.

```sql
INSERT INTO users (name, email) VALUES ('Alice', 'alice@example.com')
RETURNING id, created_at;

UPDATE products SET price = price * 1.1 WHERE category = 'electronics'
RETURNING id, name, price;
```

---

### Q64. What is `INSERT ... ON CONFLICT` (UPSERT)?
**Answer:** Upsert inserts a row if it doesn't exist, or updates it if there's a conflict on a unique constraint.

```sql
INSERT INTO user_settings (user_id, theme)
VALUES (1, 'dark')
ON CONFLICT (user_id)
DO UPDATE SET theme = EXCLUDED.theme;
```

`EXCLUDED` refers to the row that was proposed for insertion.

---

### Q65. How do you perform bulk inserts efficiently?
**Answer:**
1. Use multi-row `INSERT VALUES`: `INSERT INTO t VALUES (1,'a'), (2,'b'), ...`
2. Use `COPY` command (fastest — bypasses most overhead):
```sql
COPY products (name, price) FROM '/tmp/products.csv' CSV HEADER;
```
3. From application code, use batched prepared statements.
4. Disable triggers/indexes during load, then rebuild.

---

### Q66. What is the `COPY` command?
**Answer:** `COPY` is PostgreSQL's bulk data import/export command. It's significantly faster than individual `INSERT` statements because it bypasses WAL logging overhead and uses efficient binary transfer.

```sql
COPY employees TO '/tmp/emp.csv' CSV HEADER;
COPY employees FROM '/tmp/emp.csv' CSV HEADER;
\copy employees FROM 'local_file.csv' CSV HEADER;  -- psql client-side version
```

---

### Q67. How do you paginate results efficiently?
**Answer:**
- **Offset pagination**: `LIMIT n OFFSET m` — simple but slow for large offsets (must scan and discard rows).
- **Keyset/cursor pagination**: Filter by last seen value — much more efficient for large datasets.

```sql
-- Keyset pagination (preferred for performance)
SELECT * FROM orders
WHERE (created_at, id) < ('2024-01-15', 1000)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

---

### Q68. What is the `FILTER` clause in aggregates?
**Answer:** `FILTER` allows conditional aggregation, counting/summing only rows that match a condition.

```sql
SELECT
  COUNT(*) FILTER (WHERE status = 'active') AS active_users,
  COUNT(*) FILTER (WHERE status = 'inactive') AS inactive_users
FROM users;
```

---

### Q69. What is `COALESCE`?
**Answer:** `COALESCE` returns the first non-NULL value from its argument list. Useful for providing default values.

```sql
SELECT COALESCE(nickname, first_name, 'Anonymous') AS display_name FROM users;
```

---

### Q70. What is `NULLIF`?
**Answer:** `NULLIF(a, b)` returns `NULL` if `a = b`, otherwise returns `a`. Useful for avoiding division-by-zero errors.

```sql
SELECT total / NULLIF(quantity, 0) AS unit_price FROM orders;
```

---

### Q71. What is `GREATEST` and `LEAST`?
**Answer:** `GREATEST` returns the largest value from a list; `LEAST` returns the smallest. Unlike `MAX`/`MIN`, they work across columns rather than rows.

```sql
SELECT GREATEST(price, min_price) AS effective_price FROM products;
```

---

### Q72. What are aggregate functions in PostgreSQL?
**Answer:** Common aggregate functions: `COUNT()`, `SUM()`, `AVG()`, `MIN()`, `MAX()`, `STRING_AGG()`, `ARRAY_AGG()`, `JSON_AGG()`, `JSONB_AGG()`, `BOOL_AND()`, `BOOL_OR()`, `BIT_AND()`, `BIT_OR()`, `PERCENTILE_CONT()`, `PERCENTILE_DISC()`, `MODE()`.

---

### Q73. What is `STRING_AGG`?
**Answer:** `STRING_AGG` concatenates strings from multiple rows into a single string with a delimiter.

```sql
SELECT department, STRING_AGG(name, ', ' ORDER BY name) AS members
FROM employees
GROUP BY department;
```

---

### Q74. What is `ARRAY_AGG`?
**Answer:** `ARRAY_AGG` collects values from multiple rows into an array.

```sql
SELECT user_id, ARRAY_AGG(tag ORDER BY tag) AS tags
FROM user_tags
GROUP BY user_id;
```

---

### Q75. How do you generate a series of numbers or dates?
**Answer:** Use `generate_series()`:

```sql
SELECT generate_series(1, 10);
SELECT generate_series('2024-01-01'::date, '2024-12-31', '1 month')::date;
```

---

### Q76. What is the `CASE` expression?
**Answer:** `CASE` provides conditional logic inside queries.

```sql
SELECT name,
  CASE
    WHEN salary > 100000 THEN 'Senior'
    WHEN salary > 60000  THEN 'Mid'
    ELSE 'Junior'
  END AS level
FROM employees;
```

---

### Q77. What are the string functions available in PostgreSQL?
**Answer:** Key string functions: `LENGTH()`, `UPPER()`, `LOWER()`, `TRIM()`, `LTRIM()`, `RTRIM()`, `SUBSTRING()`, `POSITION()`, `REPLACE()`, `SPLIT_PART()`, `REGEXP_MATCH()`, `REGEXP_REPLACE()`, `CONCAT()`, `LPAD()`, `RPAD()`, `MD5()`, `ENCODE()`, `DECODE()`, `FORMAT()`.

---

### Q78. What are date/time functions in PostgreSQL?
**Answer:** Key date/time functions: `NOW()`, `CURRENT_TIMESTAMP`, `CURRENT_DATE`, `CURRENT_TIME`, `DATE_TRUNC()`, `DATE_PART()`, `EXTRACT()`, `AGE()`, `TO_TIMESTAMP()`, `TO_CHAR()`, `MAKE_DATE()`, `MAKE_INTERVAL()`, `AT TIME ZONE`.

```sql
SELECT DATE_TRUNC('month', NOW());                  -- first of current month
SELECT EXTRACT(DOW FROM CURRENT_DATE);              -- day of week (0=Sunday)
SELECT AGE('2000-01-15'::date);                    -- interval since date
```

---

### Q79. How does PostgreSQL handle `NULL`?
**Answer:** `NULL` represents an unknown or missing value. Key behaviors:
- Any arithmetic with `NULL` yields `NULL`
- `NULL = NULL` is `NULL` (not `TRUE`) — use `IS NULL` or `IS DISTINCT FROM`
- Aggregates ignore `NULL` (except `COUNT(*)`)
- `ORDER BY` puts NULLs last by default (ascending), first (descending). Override with `NULLS FIRST` / `NULLS LAST`

---

### Q80. What is `GROUPING SETS`, `ROLLUP`, and `CUBE`?
**Answer:** These are advanced grouping extensions:
- `GROUPING SETS ((a), (b), ())` — specify exactly which groupings to compute
- `ROLLUP (a, b, c)` — computes all prefix subtotals: `(a,b,c)`, `(a,b)`, `(a)`, `()`
- `CUBE (a, b, c)` — computes all possible grouping combinations (2^n)

```sql
SELECT year, quarter, SUM(sales) FROM data
GROUP BY ROLLUP (year, quarter);
```

## Indexes & Performance

### Q81. What is an index in PostgreSQL?
**Answer:** An index is a data structure that improves the speed of data retrieval operations on a table at the cost of additional storage and slower write operations. PostgreSQL supports multiple index types, each optimized for different query patterns.

---

### Q82. What are the index types in PostgreSQL?
**Answer:**
- **B-tree** (default) — equality and range queries, `<`, `>`, `BETWEEN`, `LIKE 'foo%'`
- **Hash** — equality only (`=`), faster than B-tree for exact lookups
- **GIN** (Generalized Inverted Index) — arrays, JSONB, full-text search (multi-value columns)
- **GiST** (Generalized Search Tree) — geometric types, full-text, range types
- **SP-GiST** (Space-Partitioned GiST) — non-balanced structures (quadtrees, k-d trees)
- **BRIN** (Block Range Index) — very large tables with naturally ordered data (timestamps, sequential IDs) — tiny size

---

### Q83. When should you use a GIN index?
**Answer:** GIN indexes are ideal for columns containing multiple values where you want to search for any of those values:
- `JSONB` columns (for `@>`, `?`, `?|`, `?&` operators)
- Array columns (for `@>`, `&&` operators)
- Full-text search (`tsvector` columns)

```sql
CREATE INDEX idx_products_tags ON products USING GIN (tags);
CREATE INDEX idx_users_data ON users USING GIN (data); -- JSONB
```

---

### Q84. What is a partial index?
**Answer:** A partial index only indexes rows that satisfy a `WHERE` condition, making it smaller and faster than a full index.

```sql
CREATE INDEX idx_active_users ON users (email) WHERE is_active = TRUE;
CREATE INDEX idx_pending_orders ON orders (created_at) WHERE status = 'pending';
```

---

### Q85. What is a covering index (include columns)?
**Answer:** A covering index includes extra columns (via `INCLUDE`) that are stored in the index leaf pages but not used as index keys. Queries that only access included columns can be satisfied from the index alone (index-only scan), avoiding heap access.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id) INCLUDE (total, created_at);
```

---

### Q86. What is a composite index?
**Answer:** A composite (multi-column) index covers multiple columns. Column order matters — it's efficient for queries that filter on the leftmost columns.

```sql
CREATE INDEX idx_orders_customer_date ON orders (customer_id, created_at DESC);
-- Efficient for: WHERE customer_id = X ORDER BY created_at DESC
-- NOT efficient for: WHERE created_at > X (without customer_id)
```

---

### Q87. What is an expression index?
**Answer:** An expression index is built on the result of a function or expression rather than a raw column value.

```sql
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
-- Enables: WHERE LOWER(email) = 'alice@example.com'
```

---

### Q88. What is a unique index?
**Answer:** A unique index ensures no two rows have the same value(s) in the indexed column(s). `UNIQUE` constraints are automatically implemented as unique indexes.

```sql
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

---

### Q89. What is an index scan vs a sequential scan?
**Answer:**
- **Sequential scan** — reads every row in the table. Efficient when returning a large fraction of rows.
- **Index scan** — follows the index to find matching rows, then fetches from heap. Efficient for high-selectivity queries (few matching rows).
- **Index-only scan** — all needed data is in the index, heap not accessed. Fastest.
- **Bitmap index scan** — PostgreSQL scans the index, builds a bitmap of matching pages, then fetches pages in physical order. Good for medium selectivity.

---

### Q90. How do you identify slow queries?
**Answer:**
1. Enable `pg_stat_statements` to track query performance
2. Set `log_min_duration_statement` in `postgresql.conf` to log slow queries
3. Use `EXPLAIN ANALYZE` on specific queries
4. Query `pg_stat_activity` for currently running queries
5. Use monitoring tools: PgBadger, pganalyze, DataDog

---

### Q91. What does `EXPLAIN` output tell you?
**Answer:** Key things to look for in `EXPLAIN ANALYZE` output:
- **Seq Scan** on a large table (should it be an index scan?)
- **Rows** discrepancy between estimated and actual (stale statistics?)
- **Loops** — how many times an operation is repeated
- **Cost** — planner's estimate (startup cost .. total cost)
- **Buffers** — pages read from disk vs. cache (with `BUFFERS` option)
- **Sort** on disk (needs larger `work_mem`)

---

### Q92. What is index bloat?
**Answer:** Index bloat occurs when indexes accumulate dead entries from updates and deletes that haven't been reclaimed. Bloated indexes waste space and slow down queries. Use `REINDEX` or `pgstattuple` to detect and fix bloat.

---

### Q93. What is the `REINDEX` command?
**Answer:** `REINDEX` rebuilds an index, removing bloat and fixing corruption. `REINDEX CONCURRENTLY` (PostgreSQL 12+) rebuilds without holding an exclusive lock.

```sql
REINDEX INDEX idx_users_email;
REINDEX TABLE users;
REINDEX CONCURRENTLY INDEX idx_users_email;
```

---

### Q94. What is `work_mem` and how does it affect performance?
**Answer:** `work_mem` is the memory allocated per sort or hash operation **per query node**. Complex queries can use multiple times this amount. Setting it too low causes sorts to spill to disk (slow); too high can cause out-of-memory errors with many concurrent queries. Typical values: 4MB–256MB depending on workload.

---

### Q95. What is `effective_cache_size`?
**Answer:** `effective_cache_size` tells the query planner how much total memory is available for caching (shared buffers + OS cache). It doesn't allocate memory — it's just a hint that helps the planner decide whether index scans (which need cached pages) are worthwhile. Typically set to 50–75% of total RAM.

---

### Q96. How does `autovacuum` relate to query performance?
**Answer:** If autovacuum doesn't run frequently enough, dead tuples accumulate, bloating tables and indexes. This slows down sequential scans and causes table bloat. Additionally, without fresh statistics, the planner makes poor decisions. Tuning `autovacuum_vacuum_cost_delay`, `autovacuum_vacuum_scale_factor`, and `autovacuum_analyze_scale_factor` is important for busy tables.

---

### Q97. What is the HOT update optimization?
**Answer:** Heap-Only Tuple (HOT) updates occur when an updated row fits on the same page and no indexed columns changed. PostgreSQL creates a chain from the old to new tuple without updating indexes. This significantly reduces index write overhead for updates that don't change indexed columns.

---

### Q98. What is `pg_trgm` and how does it enable fast LIKE searches?
**Answer:** `pg_trgm` (trigram extension) breaks text into 3-character substrings. It enables GIN or GiST indexes to support `LIKE '%foo%'` and `ILIKE '%foo%'` queries efficiently (which regular B-tree indexes can't handle mid-string).

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
SELECT * FROM products WHERE name ILIKE '%wireless%';
```

---

### Q99. What is `connection_limit` and why does it matter?
**Answer:** Each PostgreSQL connection consumes a backend process with ~5–10 MB of memory. `max_connections` (default 100) limits total connections. Exceeding it causes connection errors. Use PgBouncer or Pgpool-II for connection pooling at scale.

---

### Q100. What is table partitioning in PostgreSQL?
**Answer:** Partitioning splits a large table into smaller physical pieces (partitions) while presenting them as one logical table. Types:
- **Range partitioning** — by ranges of a column (e.g., by month)
- **List partitioning** — by explicit values (e.g., by country)
- **Hash partitioning** — by hash of a column value

```sql
CREATE TABLE orders (id BIGINT, created_at DATE, total NUMERIC)
PARTITION BY RANGE (created_at);

CREATE TABLE orders_2024 PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

---

### Q101. What are the benefits of partitioning?
**Answer:**
- **Partition pruning** — queries only scan relevant partitions
- **Faster bulk deletes** — drop entire partitions instead of row-by-row delete
- **Easier archival** — detach old partitions and archive
- **Better cache utilization** — frequently accessed partitions stay in memory
- **Parallel query** — partitions can be scanned in parallel

---

### Q102. What is a materialized view?
**Answer:** A materialized view stores the result of a query physically on disk. Unlike regular views, the data is precomputed and must be explicitly refreshed.

```sql
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT DATE_TRUNC('month', created_at) AS month, SUM(total) AS revenue
FROM orders GROUP BY 1;

REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;
```

---

### Q103. What is `REFRESH MATERIALIZED VIEW CONCURRENTLY`?
**Answer:** `CONCURRENTLY` refreshes the materialized view without blocking reads. It requires a unique index on the view. Without `CONCURRENTLY`, `REFRESH` locks out all reads during the refresh.

---

### Q104. What is `parallel query` in PostgreSQL?
**Answer:** PostgreSQL can use multiple CPU cores to execute parts of a query in parallel. Controlled by `max_parallel_workers_per_gather`, `parallel_setup_cost`, and `parallel_tuple_cost`. Works for sequential scans, hash joins, aggregates, and index scans (PostgreSQL 12+).

---

### Q105. What is a functional dependency and how does it affect `GROUP BY`?
**Answer:** In PostgreSQL, if a column is functionally dependent on a primary key, you don't need to include it in `GROUP BY`. For example, if you group by the primary key, all other columns of that table are implicitly included.

```sql
-- Works in PostgreSQL because name is functionally dependent on id (primary key)
SELECT id, name, COUNT(orders.*) FROM customers JOIN orders ON ... GROUP BY id;
```

---

### Q106. What is the difference between a view and a materialized view?
**Answer:**
- **View** — virtual table, query runs every time the view is accessed. Always up-to-date.
- **Materialized View** — stores results physically. Fast to query but requires manual refresh to get updated data.

---

### Q107. How do you find missing indexes?
**Answer:** Query `pg_stat_user_tables` for high `seq_scan` counts on large tables, and cross-reference with `pg_stat_user_indexes` for index usage. Low `idx_scan` on an existing index may indicate an unused index to drop.

```sql
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables
ORDER BY seq_scan DESC;
```

---

### Q108. What is the `pg_stats` view?
**Answer:** `pg_stats` shows per-column statistics gathered by `ANALYZE`: null fraction, distinct values, most common values, and histogram of value distribution. The planner uses this to estimate result sizes.

---

### Q109. What is `cursor` in PostgreSQL?
**Answer:** A cursor allows fetching rows from a result set incrementally rather than all at once. Useful for processing large result sets without loading everything into memory.

```sql
BEGIN;
DECLARE my_cursor CURSOR FOR SELECT * FROM large_table;
FETCH 100 FROM my_cursor;
CLOSE my_cursor;
COMMIT;
```

---

### Q110. What is JIT compilation in PostgreSQL?
**Answer:** JIT (Just-In-Time) compilation (PostgreSQL 11+) uses LLVM to compile parts of queries at runtime, speeding up CPU-intensive operations like expression evaluation on large datasets. Enable with `SET jit = on;`. It has overhead so is best for long-running analytical queries.

---

## Transactions & Concurrency

### Q111. How do you use transactions in PostgreSQL?
**Answer:**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK; on error
```

`SAVEPOINT` allows partial rollbacks within a transaction.

---

### Q112. What are isolation levels in PostgreSQL?
**Answer:** PostgreSQL supports four isolation levels:
- **Read Uncommitted** — same as Read Committed in PG (PG always prevents dirty reads)
- **Read Committed** (default) — sees committed data as of each statement
- **Repeatable Read** — sees committed data as of transaction start; prevents non-repeatable reads
- **Serializable** — strongest; transactions behave as if executed serially (SSI in PostgreSQL)

---

### Q113. What are the concurrency anomalies?
**Answer:**
- **Dirty read** — reading uncommitted data from another transaction (prevented in PG at all levels)
- **Non-repeatable read** — same row read twice yields different results (prevented at Repeatable Read+)
- **Phantom read** — same query returns different rows due to inserts by other transactions (prevented at Serializable)
- **Lost update** — two transactions read and overwrite the same data (prevented by `SELECT FOR UPDATE` or Repeatable Read)
- **Write skew** — two transactions read overlapping data and make decisions that conflict (only prevented at Serializable)

---

### Q114. What is `SELECT FOR UPDATE`?
**Answer:** `SELECT FOR UPDATE` locks the selected rows, preventing other transactions from modifying or locking them until the current transaction commits or rolls back.

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- safe to update without lost update risk
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

---

### Q115. What is `SELECT FOR SHARE`?
**Answer:** `SELECT FOR SHARE` acquires a shared lock — allows other readers to also `FOR SHARE` lock the rows, but prevents modifications. Less restrictive than `FOR UPDATE`.

---

### Q116. What is a deadlock?
**Answer:** A deadlock occurs when two transactions each hold a lock that the other needs, causing both to wait indefinitely. PostgreSQL detects deadlocks and kills one transaction (the "victim") with an error. Design your code to acquire locks in a consistent order to prevent deadlocks.

---

### Q117. What are advisory locks in PostgreSQL?
**Answer:** Advisory locks are application-level locks that you manage explicitly. PostgreSQL provides session-level and transaction-level advisory locks. They're useful for implementing application-level mutual exclusion (e.g., preventing duplicate cron jobs).

```sql
SELECT pg_try_advisory_lock(12345); -- returns true if lock acquired
SELECT pg_advisory_unlock(12345);
```

---

### Q118. What is optimistic locking?
**Answer:** Optimistic locking assumes conflicts are rare. Instead of locking rows, it uses a version column. On update, it checks that the version hasn't changed since read; if it has, it retries.

```sql
UPDATE products SET price = 99, version = version + 1
WHERE id = 1 AND version = 5; -- 0 rows updated means conflict
```

---

### Q119. What is a `SAVEPOINT`?
**Answer:** A `SAVEPOINT` creates a point within a transaction to which you can roll back without rolling back the entire transaction.

```sql
BEGIN;
INSERT INTO orders ...;
SAVEPOINT before_payment;
INSERT INTO payments ...;
ROLLBACK TO before_payment; -- undo payment only
COMMIT; -- order is still committed
```

---

### Q120. How does PostgreSQL handle long-running transactions?
**Answer:** Long-running transactions prevent VACUUM from reclaiming dead tuples (they might still be visible to the old transaction), leading to table bloat. Monitor with `pg_stat_activity` and set `idle_in_transaction_session_timeout` to kill stuck transactions.

---

### Q121. What is `pg_stat_activity`?
**Answer:** `pg_stat_activity` is a system view showing one row per backend process, including the query being executed, wait event, transaction start time, client address, and state (`active`, `idle`, `idle in transaction`).

```sql
SELECT pid, state, query, now() - query_start AS duration
FROM pg_stat_activity WHERE state != 'idle' ORDER BY duration DESC;
```

---

### Q122. How do you kill a query or connection?
**Answer:**

```sql
SELECT pg_cancel_backend(pid);   -- cancel query, keep connection
SELECT pg_terminate_backend(pid); -- terminate backend completely
```

---

### Q123. What is `lock_timeout` and `statement_timeout`?
**Answer:**
- `statement_timeout` — aborts any statement that runs longer than the specified duration.
- `lock_timeout` — aborts a statement if it can't acquire a lock within the specified time.
- `idle_in_transaction_session_timeout` — terminates sessions idle in a transaction for too long.

```sql
SET statement_timeout = '30s';
SET lock_timeout = '5s';
```

---

### Q124. What is row-level locking vs table-level locking?
**Answer:**
- **Row-level locks** — `SELECT FOR UPDATE/SHARE` locks specific rows. Fine-grained, low contention.
- **Table-level locks** — `LOCK TABLE` or implicit locks from DDL (`ALTER TABLE`, `CREATE INDEX`). Coarser, can block all access.
PostgreSQL uses the weakest lock necessary for each operation.

---

### Q125. What is SSI (Serializable Snapshot Isolation)?
**Answer:** PostgreSQL's Serializable isolation level uses SSI, which detects and prevents serialization anomalies (including write skew and phantom reads) without heavy locking. It uses dependency tracking between transactions and aborts conflicting ones with a "could not serialize access" error.

---

### Q126. What is two-phase commit (2PC)?
**Answer:** Two-phase commit is a protocol for distributed transactions across multiple databases. In phase 1, the coordinator asks all participants to prepare. In phase 2, if all succeed, it commits; otherwise, all roll back. PostgreSQL supports it with `PREPARE TRANSACTION` and `COMMIT PREPARED`.

---

### Q127. What are implicit locks in PostgreSQL?
**Answer:** DDL statements acquire strong table-level locks automatically. For example, `ALTER TABLE` acquires `AccessExclusiveLock`, blocking all reads and writes. Use `CREATE INDEX CONCURRENTLY` or `pg_repack` to avoid blocking production tables.

---

### Q128. What is `CREATE INDEX CONCURRENTLY`?
**Answer:** `CREATE INDEX CONCURRENTLY` builds an index without holding a lock that blocks writes. It performs multiple scans of the table and takes longer, but allows normal read/write operations during index creation.

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer ON orders (customer_id);
```

---

### Q129. What is a transaction ID (XID) wraparound?
**Answer:** PostgreSQL uses 32-bit transaction IDs. After ~2 billion transactions, XIDs wrap around, which can make old data appear to be "in the future" causing data loss. VACUUM's job includes marking old rows as frozen (not needing an XID comparison). Monitoring `pg_database.datfrozenxid` prevents this catastrophic issue.

---

### Q130. What is `SKIP LOCKED`?
**Answer:** `SKIP LOCKED` skips rows that are currently locked by other transactions, instead of waiting. Useful for implementing job queues where multiple workers process different tasks concurrently.

```sql
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

---

## Advanced PostgreSQL

### Q131. What are stored functions in PostgreSQL?
**Answer:** Functions are stored, reusable SQL/procedural code. PostgreSQL supports multiple languages: `SQL`, `PL/pgSQL`, `PL/Python`, `PL/Perl`, `PL/v8` (JavaScript).

```sql
CREATE OR REPLACE FUNCTION get_user_count()
RETURNS INTEGER AS $$
  SELECT COUNT(*) FROM users;
$$ LANGUAGE SQL;

SELECT get_user_count();
```

---

### Q132. What is PL/pgSQL?
**Answer:** PL/pgSQL is PostgreSQL's built-in procedural language. It supports variables, conditionals, loops, exception handling, and cursor processing — much more powerful than plain SQL functions.

```sql
CREATE OR REPLACE FUNCTION calculate_discount(price NUMERIC, category TEXT)
RETURNS NUMERIC AS $$
DECLARE
  discount_rate NUMERIC;
BEGIN
  IF category = 'premium' THEN discount_rate := 0.2;
  ELSE discount_rate := 0.1;
  END IF;
  RETURN price * (1 - discount_rate);
END;
$$ LANGUAGE plpgsql;
```

---

### Q133. What are triggers in PostgreSQL?
**Answer:** Triggers are functions that automatically execute in response to events (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`) on a table, either `BEFORE` or `AFTER` (or `INSTEAD OF` for views).

```sql
CREATE OR REPLACE FUNCTION update_timestamp()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_timestamp
BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION update_timestamp();
```

---

### Q134. What is the difference between row-level and statement-level triggers?
**Answer:**
- **Row-level** (`FOR EACH ROW`) — fires once per affected row. Has access to `OLD` and `NEW` row records.
- **Statement-level** (`FOR EACH STATEMENT`) — fires once per SQL statement regardless of how many rows are affected. Better performance for bulk operations.

---

### Q135. What are `BEFORE` vs `AFTER` triggers?
**Answer:**
- `BEFORE` triggers fire before the operation and can modify `NEW` (for row-level) to change what gets written, or return `NULL` to skip the operation.
- `AFTER` triggers fire after the operation is complete. They can't modify row data but can perform actions based on the final state.

---

### Q136. What are event triggers?
**Answer:** Event triggers (PostgreSQL 9.3+) fire on DDL events (`ddl_command_start`, `ddl_command_end`, `sql_drop`) rather than DML events. Useful for auditing DDL changes or enforcing naming conventions.

---

### Q137. What are foreign data wrappers (FDW)?
**Answer:** FDWs allow PostgreSQL to query external data sources as if they were local tables. The `postgres_fdw` wrapper queries other PostgreSQL databases; `file_fdw` reads CSV files; others exist for MySQL, Oracle, Redis, MongoDB, S3, etc.

```sql
CREATE EXTENSION postgres_fdw;
CREATE SERVER remote_db FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'remote', dbname 'analytics');
CREATE FOREIGN TABLE remote_orders (...) SERVER remote_db;
```

---

### Q138. What is table inheritance in PostgreSQL?
**Answer:** A table can inherit from one or more parent tables, automatically including all parent columns. Queries on the parent include child table rows (with `ONLY` keyword to exclude children). Largely superseded by declarative partitioning for most use cases.

```sql
CREATE TABLE vehicles (id SERIAL, make TEXT, model TEXT);
CREATE TABLE cars () INHERITS (vehicles);
CREATE TABLE trucks (payload_tons NUMERIC) INHERITS (vehicles);
```

---

### Q139. What are generated columns?
**Answer:** Generated columns (PostgreSQL 12+) are computed from other columns using an expression. They are always calculated and stored (or computed on read for virtual, not yet supported).

```sql
CREATE TABLE products (
  price NUMERIC,
  tax_rate NUMERIC DEFAULT 0.1,
  price_with_tax NUMERIC GENERATED ALWAYS AS (price * (1 + tax_rate)) STORED
);
```

---

### Q140. What is `LISTEN` and `NOTIFY`?
**Answer:** `NOTIFY` sends an asynchronous notification on a named channel; `LISTEN` subscribes to it. This enables real-time pub/sub between PostgreSQL sessions or between the database and application code.

```sql
-- Session 1:
LISTEN order_updates;

-- Session 2:
NOTIFY order_updates, 'Order 123 shipped';

-- Session 1 receives the notification asynchronously
```

---

### Q141. What is logical decoding in PostgreSQL?
**Answer:** Logical decoding extracts the logical meaning of WAL changes (row-level inserts/updates/deletes) in a human-readable format via output plugins. It powers logical replication and tools like Debezium for change data capture (CDC).

---

### Q142. What are publications and subscriptions?
**Answer:** Publications define what tables to replicate; subscriptions connect to a publisher and receive changes.

```sql
-- On publisher:
CREATE PUBLICATION my_pub FOR TABLE orders, products;

-- On subscriber:
CREATE SUBSCRIPTION my_sub CONNECTION '...' PUBLICATION my_pub;
```

---

### Q143. What is `pg_partman`?
**Answer:** `pg_partman` is an extension that automates partition management in PostgreSQL — automatically creating future partitions and dropping old ones based on a time or serial-number based strategy.

---

### Q144. What is `pg_cron`?
**Answer:** `pg_cron` is an extension that runs scheduled PostgreSQL jobs using cron syntax, directly inside the database — similar to OS cron but for SQL tasks.

```sql
SELECT cron.schedule('0 * * * *', $$REFRESH MATERIALIZED VIEW monthly_sales$$);
```

---

### Q145. What is `pg_repack`?
**Answer:** `pg_repack` is an extension that reclaims bloat from tables and indexes without holding exclusive locks (unlike `VACUUM FULL` or `CLUSTER`). Essential for reducing bloat in production without downtime.

---

### Q146. What is full-text search in PostgreSQL?
**Answer:** PostgreSQL has built-in FTS using `TSVECTOR` and `TSQUERY`. Text is tokenized, stemmed, and stop words removed. GIN indexes make searches fast.

```sql
ALTER TABLE articles ADD COLUMN search_vector TSVECTOR;
UPDATE articles SET search_vector = to_tsvector('english', title || ' ' || body);
CREATE INDEX idx_fts ON articles USING GIN (search_vector);
SELECT * FROM articles WHERE search_vector @@ plainto_tsquery('english', 'PostgreSQL performance');
```

---

### Q147. What is `websearch_to_tsquery`?
**Answer:** `websearch_to_tsquery` (PostgreSQL 11+) parses a web-search-like query string, supporting quoted phrases, `AND`/`OR`, and `-` for exclusion without needing special syntax.

```sql
SELECT websearch_to_tsquery('english', '"full text" search -slow');
```

---

### Q148. What are domain types in PostgreSQL?
**Answer:** A domain is a user-defined type based on an existing type with optional constraints. It enforces business rules at the type level.

```sql
CREATE DOMAIN positive_numeric AS NUMERIC CHECK (VALUE > 0);
CREATE DOMAIN valid_email AS TEXT CHECK (VALUE ~* '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$');

CREATE TABLE orders (amount positive_numeric, customer_email valid_email);
```

---

### Q149. What is `pg_replication_slot`?
**Answer:** A replication slot ensures that the primary doesn't delete WAL segments that a subscriber still needs, preventing WAL-based subscribers from falling behind and losing data. They must be monitored — inactive slots can cause unbounded WAL accumulation.

---

### Q150. What is `CLUSTER` in PostgreSQL?
**Answer:** `CLUSTER` physically reorders a table's rows according to an index, co-locating related rows on disk for better sequential access patterns. It requires an exclusive lock and is not maintained automatically — `REINDEX` and inserts will gradually un-cluster the data.

```sql
CLUSTER orders USING idx_orders_customer;
```

---

### Q151. What are exclusion constraints?
**Answer:** Exclusion constraints (using GiST indexes) ensure that for any two rows, at least one specified comparison fails. Useful for preventing overlapping time ranges or bookings.

```sql
CREATE TABLE bookings (
  room_id INT,
  during TSTZRANGE,
  EXCLUDE USING GIST (room_id WITH =, during WITH &&)
);
```

---

### Q152. What is `UNNEST`?
**Answer:** `UNNEST` expands an array (or multiple arrays) into a set of rows, making array elements easy to query with standard SQL.

```sql
SELECT UNNEST(ARRAY['a', 'b', 'c']) AS element;
SELECT UNNEST(tags) AS tag, COUNT(*) FROM products GROUP BY tag;
```

---

### Q153. What are `crosstab` / pivot queries?
**Answer:** PostgreSQL supports pivot (crosstab) queries via the `tablefunc` extension's `crosstab()` function, which transforms row values into column headers.

```sql
CREATE EXTENSION tablefunc;
SELECT * FROM crosstab(
  'SELECT user_id, month, revenue FROM monthly_revenue ORDER BY 1, 2'
) AS ct (user_id INT, jan NUMERIC, feb NUMERIC, mar NUMERIC);
```

---

### Q154. What is `pg_audit`?
**Answer:** `pgaudit` is an extension that provides detailed session and object auditing logging, recording which SQL statements were executed and by whom. Essential for compliance (HIPAA, SOC2, etc.).

---

### Q155. What is connection pooling and why is it needed?
**Answer:** PostgreSQL is process-based — each connection spawns a new OS process (~5-10 MB RAM). Many connections from a web application exhaust memory and slow down the server. A connection pooler (PgBouncer) maintains a smaller pool of backend connections and queues client requests, dramatically reducing overhead.

---

### Q156. What are the PgBouncer pooling modes?
**Answer:**
- **Session pooling** — one server connection per client session. Safe but limited pooling.
- **Transaction pooling** — server connection returned to pool after each transaction. Most efficient; doesn't support all features (prepared statements, `LISTEN`).
- **Statement pooling** — returned after each statement. Most restrictive; rarely used.

---

### Q157. What is `EXPLAIN (BUFFERS, ANALYZE, FORMAT JSON)`?
**Answer:** The `BUFFERS` option shows cache hits and misses. `FORMAT JSON` outputs the plan in machine-readable JSON. Combined with `ANALYZE`, this gives a detailed picture of I/O patterns and execution.

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT * FROM orders WHERE customer_id = 1;
```

---

### Q158. What is the `pageinspect` extension?
**Answer:** `pageinspect` allows you to examine the raw contents of database pages (heap, index, FSM, VM pages) at a low level. Useful for understanding MVCC tuple versioning and diagnosing bloat.

---

### Q159. What is `pg_visibility`?
**Answer:** `pg_visibility` (PostgreSQL 9.6+) examines the visibility map, showing which pages are marked all-visible or all-frozen. Helps diagnose VACUUM effectiveness.

---

### Q160. What is Row-Level Security (RLS)?
**Answer:** RLS allows you to define policies that restrict which rows a user can see or modify. When enabled on a table, every query is automatically filtered by the applicable policies.

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_isolation ON documents
  USING (owner_id = current_setting('app.current_user_id')::INT);
```

---

### Q161. What is `current_setting` and `set_config`?
**Answer:** These functions get and set session-level configuration variables, often used to pass context (like the current user ID) to RLS policies or trigger functions.

```sql
SELECT set_config('app.current_user_id', '42', false); -- false = session-level
SELECT current_setting('app.current_user_id');
```

---

### Q162. What is `pg_prewarm`?
**Answer:** `pg_prewarm` loads table or index data into the PostgreSQL buffer cache (or the OS page cache) proactively after a restart, reducing cold-start performance issues.

---

### Q163. What is `logical backup` vs `physical backup`?
**Answer:**
- **Logical backup** (`pg_dump`) — exports SQL/data. Portable across versions, can be partial. Slower restore for large databases.
- **Physical backup** (`pg_basebackup`, file system snapshot) — copies data files. Fast restore, must match PostgreSQL version. Foundation for PITR.

---

### Q164. What is `pgcrypto`?
**Answer:** `pgcrypto` is an extension that provides cryptographic functions: symmetric/asymmetric encryption, hashing (`crypt`, `gen_salt`), and PGP functions. Useful for encrypting sensitive columns at the application layer before storing.

---

### Q165. What is `plv8` (PL/V8)?
**Answer:** `plv8` is an extension that lets you write PostgreSQL functions in JavaScript (using the V8 engine). It enables complex JSON manipulation, sharing validation logic between the database and Node.js backend.

---

## Administration & Security

### Q166. What are roles in PostgreSQL?
**Answer:** PostgreSQL uses roles (unified concept for users and groups). A role with `LOGIN` is a user. Roles can be members of other roles, inheriting their privileges.

```sql
CREATE ROLE developer;
CREATE ROLE alice LOGIN PASSWORD 'secret';
GRANT developer TO alice;
```

---

### Q167. What is the principle of least privilege in PostgreSQL?
**Answer:** Grant only the minimum permissions needed. Instead of using the superuser `postgres` account, create roles with specific privileges (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) on specific tables for each application.

```sql
CREATE ROLE app_user LOGIN PASSWORD 'secret';
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_user;
```

---

### Q168. What is `GRANT` and `REVOKE`?
**Answer:** `GRANT` gives privileges on objects; `REVOKE` removes them.

```sql
GRANT SELECT ON products TO read_only_role;
GRANT USAGE ON SCHEMA analytics TO analyst;
REVOKE INSERT ON orders FROM junior_dev;
```

---

### Q169. What is `DEFAULT PRIVILEGES`?
**Answer:** `ALTER DEFAULT PRIVILEGES` sets the privileges automatically granted on future objects created by a specific role. Prevents forgetting to grant access when new tables are created.

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO readonly_role;
```

---

### Q170. How do you encrypt data at rest in PostgreSQL?
**Answer:** Options:
1. **Filesystem encryption** — encrypt the entire data directory (OS-level, e.g., LUKS, dm-crypt)
2. **`pgcrypto`** — encrypt specific columns with `pgp_sym_encrypt()`
3. **Application-level encryption** — encrypt before sending to database
4. **Transparent Data Encryption (TDE)** — available in some PostgreSQL distributions (e.g., Percona, EDB)

---

### Q171. What is SSL/TLS in PostgreSQL?
**Answer:** PostgreSQL supports SSL/TLS for encrypting client-server connections. Configure with `ssl = on` in `postgresql.conf` and provide certificate files. `pg_hba.conf` can require SSL for specific connections (`hostssl`).

---

### Q172. What is the `superuser` role?
**Answer:** A superuser bypasses all access control checks and can do anything in the database. Only trusted administrators should have superuser privileges. Application accounts should never be superusers.

---

### Q173. What is `pg_dump` vs `pg_dumpall`?
**Answer:**
- `pg_dump` backs up a single database.
- `pg_dumpall` backs up all databases in a cluster, plus global objects (roles, tablespaces) that `pg_dump` doesn't capture.

---

### Q174. What is the `postgres` role?
**Answer:** `postgres` is the initial superuser role created when PostgreSQL is installed. It owns the system catalog and is used for administration. In production, you should create separate roles for applications and limit `postgres` usage.

---

### Q175. What is `pg_basebackup`?
**Answer:** `pg_basebackup` creates a physical backup of the entire PostgreSQL cluster by streaming data files over the replication protocol. It's the standard tool for taking base backups for PITR or setting up standby servers.

---

### Q176. How do you monitor PostgreSQL?
**Answer:** Key monitoring approaches:
- `pg_stat_activity` — active queries and connection states
- `pg_stat_user_tables` — table scan and DML statistics
- `pg_stat_bgwriter` — checkpoint and buffer statistics
- `pg_stat_statements` — query performance statistics
- `pg_locks` — current lock information
- External tools: Prometheus + `postgres_exporter`, Grafana, Datadog, pganalyze, PgBadger

---

### Q177. What is `check_password_strength` and password policies?
**Answer:** PostgreSQL doesn't have built-in password complexity enforcement. Use the `passwordcheck` extension to enforce minimum password requirements. For enterprise-grade policies, use external authentication (LDAP, Kerberos, SCRAM-SHA-256).

---

### Q178. What is `pg_hba.conf` authentication method `scram-sha-256`?
**Answer:** `scram-sha-256` is the most secure password authentication method in PostgreSQL (v10+). It uses the SCRAM protocol which never sends the password over the wire and stores a salted hash. Always prefer it over `md5` (deprecated) or `password` (plaintext).

---

### Q179. What are `search_path` injection attacks?
**Answer:** If `search_path` is not secured, a malicious user could create objects in the search path that shadow system functions, injecting malicious code. Mitigate by: setting `search_path` to only trusted schemas, prefixing all function calls with schema names, and using `SECURITY DEFINER` carefully.

---

### Q180. What is `SECURITY DEFINER` vs `SECURITY INVOKER`?
**Answer:**
- `SECURITY INVOKER` (default) — function runs with privileges of the caller.
- `SECURITY DEFINER` — function runs with privileges of the function owner (like `setuid` in Unix). Can be used to grant controlled access to restricted tables, but must be used carefully to avoid privilege escalation.

---

### Q181. How do you handle migrations in PostgreSQL?
**Answer:** Use migration tools: `Flyway`, `Liquibase`, `golang-migrate`, `Alembic` (Python), `Knex.js` migrations, `Prisma Migrate`. Best practices:
- Never modify existing migration files
- Make migrations idempotent where possible
- Test rollback scripts
- Apply migrations in CI/CD before deploying application code

---

### Q182. What is `zero-downtime deployment` with PostgreSQL schema changes?
**Answer:** Strategies for no-lock DDL changes:
- `CREATE INDEX CONCURRENTLY` — non-blocking
- Adding nullable columns — safe
- Adding NOT NULL with DEFAULT (PostgreSQL 11+) — safe
- Rename columns — use view/alias transition period
- Avoid `ALTER TABLE` that rewrites the table during peak traffic

---

### Q183. What is logical backup validation?
**Answer:** After taking a `pg_dump`, restore it to a test database and verify row counts, spot-check data, and run application smoke tests. Never assume a backup is valid without testing the restore.

---

### Q184. What are foreign key constraints and their performance implications?
**Answer:** Foreign keys enforce referential integrity. Each `INSERT`/`UPDATE`/`DELETE` triggers a check against the referenced table. PostgreSQL automatically creates an index on the primary key side (since PKs are unique) but does NOT automatically index the foreign key column — you must do this manually to avoid sequential scans during cascade operations.

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

---

### Q185. What is `pg_upgrade`?
**Answer:** `pg_upgrade` upgrades a PostgreSQL cluster to a new major version in-place, without a full dump/restore. It checks compatibility and migrates data files. `--link` mode uses hard links for near-instant upgrades. Always test on a copy first.

## Supabase

### Q186. What is Supabase?
**Answer:** Supabase is an open-source Firebase alternative built on top of PostgreSQL. It provides a hosted PostgreSQL database along with auto-generated REST and GraphQL APIs, real-time subscriptions, authentication, storage, and edge functions — all accessible via client libraries.

---

### Q187. What does Supabase provide out of the box?
**Answer:**
- **PostgreSQL database** — full-featured, you have direct SQL access
- **Auto-generated REST API** (via PostgREST) — instant CRUD API for all tables
- **GraphQL API** — via `pg_graphql` extension
- **Real-time** — subscribe to database changes via WebSockets
- **Authentication** — email/password, magic links, OAuth (Google, GitHub, etc.)
- **Storage** — S3-compatible file storage with access policies
- **Edge Functions** — Deno-based serverless functions
- **Dashboard** — GUI to manage tables, run SQL, set up auth

---

### Q188. What is PostgREST and how does Supabase use it?
**Answer:** PostgREST is a standalone web server that converts a PostgreSQL schema into a RESTful API automatically. Supabase runs PostgREST in front of your database, exposing every table as an API endpoint. Security is enforced via PostgreSQL roles and RLS policies.

---

### Q189. How do you query Supabase from a JavaScript/TypeScript app?
**Answer:** Use the `@supabase/supabase-js` client library:

```typescript
import { createClient } from '@supabase/supabase-js';
const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

// Select
const { data, error } = await supabase
  .from('products')
  .select('id, name, price')
  .eq('category', 'electronics')
  .order('price', { ascending: true })
  .limit(20);

// Insert
const { data, error } = await supabase
  .from('orders')
  .insert({ customer_id: 1, total: 99.99 })
  .select();
```

---

### Q190. How does authentication work in Supabase?
**Answer:** Supabase Auth manages users in a separate `auth.users` table. Upon login, it issues JWTs (JSON Web Tokens). The JWT contains the user's ID and role, and is sent with every API request. PostgreSQL's RLS policies read the JWT claims (via `auth.uid()` and `auth.role()`) to enforce per-user data access.

```sql
-- RLS policy using Supabase Auth
CREATE POLICY "Users can view own data"
ON profiles FOR SELECT
USING (auth.uid() = user_id);
```

---

### Q191. What is `auth.uid()` in Supabase?
**Answer:** `auth.uid()` is a PostgreSQL function provided by Supabase that returns the `UUID` of the currently authenticated user from the JWT. It's the primary way to write RLS policies that scope data to the logged-in user.

---

### Q192. What is the Supabase `anon` key vs `service_role` key?
**Answer:**
- **`anon` key** — public key used in client-side code. Supabase applies RLS policies for the anonymous role. Safe to expose.
- **`service_role` key** — bypasses all RLS policies. Should **never** be used in client-side code — only in trusted server-side environments (backend, edge functions, admin scripts).

---

### Q193. How do you set up Row-Level Security in Supabase?
**Answer:**

```sql
-- 1. Enable RLS on the table
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- 2. Create policies
CREATE POLICY "Anyone can read published posts"
  ON posts FOR SELECT USING (published = true);

CREATE POLICY "Authors can CRUD own posts"
  ON posts FOR ALL
  USING (auth.uid() = author_id)
  WITH CHECK (auth.uid() = author_id);
```

---

### Q194. What is Supabase Realtime?
**Answer:** Supabase Realtime uses logical replication to stream database changes (INSERT, UPDATE, DELETE) to connected clients via WebSockets. Clients subscribe to specific tables, schemas, or filtered rows.

```typescript
const channel = supabase
  .channel('orders-changes')
  .on('postgres_changes', {
    event: 'INSERT',
    schema: 'public',
    table: 'orders',
    filter: `customer_id=eq.${userId}`,
  }, (payload) => console.log(payload.new))
  .subscribe();
```

---

### Q195. What are Supabase Edge Functions?
**Answer:** Edge Functions are Deno-based TypeScript serverless functions deployed globally at the edge. They run outside the database and are ideal for webhooks, third-party API integrations, and logic that shouldn't be in the database or client.

```typescript
// supabase/functions/send-email/index.ts
Deno.serve(async (req) => {
  const { to, subject } = await req.json();
  // call email provider API...
  return new Response(JSON.stringify({ sent: true }));
});
```

---

### Q196. What is Supabase Storage?
**Answer:** Supabase Storage provides S3-compatible object storage. Files are organized in buckets with public or private visibility. Access is controlled via storage policies (similar to RLS) that can reference the authenticated user.

```typescript
// Upload
const { data, error } = await supabase.storage
  .from('avatars')
  .upload(`${userId}/avatar.png`, file);

// Get public URL
const { data } = supabase.storage.from('avatars').getPublicUrl('path/to/file.png');
```

---

### Q197. What is the Supabase `public` schema vs other schemas?
**Answer:** PostgREST (and thus the Supabase client library) exposes tables in the `public` schema by default. Tables in other schemas can be exposed by configuring `db_schema` in PostgREST settings. Sensitive tables (like internal audit logs) should be kept in non-exposed schemas.

---

### Q198. How do you run custom SQL in Supabase?
**Answer:** Three ways:
1. **SQL Editor** in the Supabase Dashboard
2. **Supabase client** `rpc()` to call PostgreSQL functions:
```typescript
const { data, error } = await supabase.rpc('get_top_products', { limit_count: 10 });
```
3. **Direct connection** using `pg` or `postgres.js` with the connection string from project settings.

---

### Q199. What are Supabase database migrations?
**Answer:** Supabase uses a `supabase/migrations` folder containing timestamped SQL files managed by the Supabase CLI. Migrations are applied in order and tracked in `supabase_migrations.schema_migrations`.

```bash
supabase migration new create_orders_table  # creates a new migration file
supabase db push                             # apply migrations to remote
supabase db reset                            # reset local DB and re-apply all
```

---

### Q200. What are Supabase database functions vs Edge Functions?
**Answer:**
- **Database functions** (PostgreSQL functions) — run inside the database engine. Ideal for: complex queries, triggers, computed columns, business logic that needs direct data access with no network round-trips. Called via `supabase.rpc()`.
- **Edge Functions** (Deno/TypeScript) — run at the network edge. Ideal for: external API calls, webhooks, sending emails, processing that requires secrets not safe in the database, or long-running tasks.

Choose database functions when you need speed and data proximity; choose Edge Functions when you need external integrations or complex server-side logic.
